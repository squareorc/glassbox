## Abstract

Large language models are increasingly asked questions about sensitive records, which raises two problems at once: the model sees identities it doesn't need, and the user can't tell whether its answer is true. GlassBox is a local question-answering pipeline over clinical notes in which both properties are enforced *and measured*. Notes are redacted before indexing; the user's question is redacted too; retrieval selects only a few short sections; a code-level guard refuses questions about a named person before the model runs; a local 7B model must cite a source for every claim; an independent NLI model checks each claim against what it cites; and every step is written to an audit trace.

On 2,500 synthetic notes and 390 evaluation questions (results on a held-out test split with bootstrap 95% CIs), GlassBox reaches **0.858** grounded accuracy [0.815, 0.899] against **0.833** for the same pipeline without privacy, i.e. no measurable utility cost. It answers **0 of 84** questions about named people (the no-privacy baseline answers 42 and leaks the person's true value in 16), leaves **0.04%** of PII values even partly visible in its index, and has **0** PII values in 9,630 log and trace records. The verifier catches **99.4%** of corrupted claims and wrongly flags 1.2% of clean genuine ones; answers it marks VERIFIED are correct 0.906 of the time, against 0.492 for the rest. Held-out tests show the limits: on unseen question wording grounded accuracy falls to 0.502, and on unseen note formats 0.819 of PII values are fully masked. Verification also cannot detect an answer about the wrong person, which is why identity protection has to happen before generation.

## 1. Introduction

### 1.1 Motivation

A conventional retrieval-augmented generation (RAG) system passes whole documents to a model. Applied to medical notes, that exposes names, record numbers and addresses the question never needed, and the fluent answer that comes back gives no way to check which parts are supported. The two problems interact: the more a system hides, the less a user can see of what the model saw, so privacy without transparency asks for blind trust exactly when trust is hardest to justify.

### 1.2 Research question

*Can a practical LLM pipeline enforce data minimisation and verifiable evidence-tracing together, in one auditable system, and what does each cost in answer quality?*

### 1.3 Contributions

1. A working, local pipeline that integrates PII redaction (of notes and questions), access-controlled minimal retrieval, cited generation with a pre-generation refusal guard, and independent claim verification, with a complete per-question audit trace.
2. An evaluation along three axes (privacy, utility, faithfulness) with dev/test discipline, confidence intervals, a no-privacy baseline and a guard-off ablation.
3. Held-out robustness tests (reworded questions, unseen note formats) committed to version control before any fix, which quantify how far the in-distribution numbers generalise.
4. Negative and methodological findings: claim-level verification cannot catch misattribution under redaction; plain answer accuracy can be gamed; approximate nearest-neighbour search silently weakened and destabilised a baseline.

## 2. System design

### 2.1 Pipeline

```
question ─► question redaction ─► query analysis ─► hybrid retrieval ─► abstain guard ─► cited generation ─► claim verification ─► answer + audit trace
```

| Stage | What it does | Why this way |
|---|---|---|
| Note redaction (offline) | Presidio + spaCy with custom recognizers; PII replaced by type tags (`[NAME]`, `[PATIENT_ID]`, …) | The index, and therefore the model, only ever holds redacted text |
| Question redaction | Same detector plus question-only name rules; records which identifier *types* were found | A name typed into the question must not reach the embedding, the logs or the prompt |
| Query analysis | Diagnosis and date phrases → metadata filters; scope → k (5 or 10); ask/condition split for multi-patient questions | Exact constraints are enforced by filters, not hoped for from similarity |
| Retrieval | Section chunks; exact dense search + BM25, fused 2:1; low-information demotion; note-grouped and two-hop selection | Minimal context (≈955 characters) that still contains the answer |
| Abstain guard | Refuses before the model is called if the question identifies a person, or if no note matches its conditions | The model can't be argued out of a code rule, and the refusal reason is logged |
| Generation | Qwen2.5-7B-Instruct, 4-bit, MLX, greedy; JSON claims each citing sources | Local (no data leaves the machine), reproducible, machine-checkable claims |
| Verification | DeBERTa-v3-large NLI: each claim vs the chunk(s) it cites → SUPPORTED / CONTRADICTED / UNSUPPORTED / UNCERTAIN | A second, independent model, not the generator grading itself |
| Audit trace | One JSON file per question with every stage's inputs, outputs, scores and timings | Trust in an inspectable process rather than in the model |

The orchestrator (`glassbox/src/pipeline.py`) contains no logic of its own; it calls the same functions as the evaluation scripts. A batch run over all 390 questions reproduces the evaluation exactly (900 of 900 traces identical across three configurations), so the system shown in the demo is the system that was measured. [PROGRESS §14.1–14.2]

### 2.2 Scoping decisions

- **Synthetic data.** Real clinical data (e.g. MIMIC) needs data-use approval that didn't fit the timeline. Synthetic notes give exact ground-truth PII spans, which makes the privacy evaluation exact. The cost is external validity, stated as a limitation.
- **Local model.** A third-party API would send data off the machine at inference time and undermine the privacy claim.
- **Redaction, not formal privacy.** Differential privacy, federated learning and homomorphic encryption are out of scope; they're discussed as related work and future work.
- **No role-based access control.** The only access control is that the raw (unredacted) index requires explicit baseline access.

## 3. Data and evaluation methodology

### 3.1 Datasets [PROGRESS §3]

| | Realistic (main benchmark) | Synthetic (replication) |
|---|---|---|
| Notes | 2,500: 1,478 progress notes (3 templates incl. SOAP), 510 discharge summaries, 512 consultations | 250 single-paragraph notes, 3 templates |
| Conditions | 10 | 8 |
| PII entities | 18,041 (patient, provider, referring-physician and emergency-contact names; 6 phone and 4 ID formats) | 838 |

Generators record each PII value's exact character span (0 span errors in 18,879 entities) and pin "today" so regeneration is byte-identical.

### 3.2 Evaluation questions [PROGRESS §4]

390 realistic questions (160 synthetic), built automatically from the generators' ground truth:

| Type | n | Example | Expected |
|---|---|---|---|
| Clinical fact | 180 | "What medication was prescribed for the Essential hypertension patient whose note is dated 2024-11-10?" | Answer (the note is identified by non-PII details only) |
| Aggregate | 90 | "Which medications were prescribed to Osteoarthritis patients who presented with reduced range of motion in February 2025?" | Answer for every qualifying patient (2–4 notes) |
| Identity | 120 | "What medication is [a named person] prescribed?" | **Refuse**: under redaction the records can't say who anyone is |

Splits are 30% dev / 70% test, stratified by type. **Every design choice was made on dev; every reported number is on test** (273 questions: 126 fact, 63 aggregate, 84 identity). Confidence intervals are percentile bootstrap over questions (5,000 resamples).

### 3.3 Metrics

- **Privacy:** typed redaction precision/recall/F1 (IoU ≥ 0.5); share of PII values fully masked; PII values visible in the index (leak audit); identity questions answered; PII values found in logs and traces.
- **Utility:** *evidence* (gold answer items present in retrieved chunks from gold notes) and **grounded accuracy**, the headline: the gold item must be in the answer *and* in a section the answer cites from a gold note. Plain accuracy (item anywhere in the answer) was replaced as headline after it proved gameable (§6.3).
- **Faithfulness:** share of corrupted claims the verifier doesn't mark SUPPORTED; false alarms on genuine claims; grounded accuracy of answers by verdict.

### 3.4 Configurations compared

| Name | Index | Question redaction | Guard | Purpose |
|---|---|---|---|---|
| GlassBox | redacted | on | on | The system |
| Raw baseline | raw | off | fallback only | The same pipeline with privacy off |
| Guard off | redacted | on | off | What the model does on its own when asked about a person |

## 4. Implementation

### 4.1 Redaction [PROGRESS §5]

Presidio's spaCy NER and regex recognizers form the base. Generic tools miss clinical formats, so custom recognizers were added: patient IDs (1–2 letters + 6 digits, dash and MRN forms, labelled numeric record numbers); dates of birth restricted to years 1936–2008 so visit dates survive; a two-layer phone recognizer (formatted numbers at 0.85; bare 10-digit numbers at 0.40, passing only with a context word such as "phone"); a structural US postal-address recognizer (house number + words + unit + city + a valid state code + ZIP, plus military addresses); and name patterns for the positions NER missed (before a credential, after a form label). A **clinical-term guard** drops NER detections made only of drug names, clinical abbreviations, measurements or form labels; before it, "Glipizide" was redacted as a name in 97 notes and destroyed three gold answers.

Engineering problems found by scaling to 2,500 notes are good report material [PROGRESS §5, tables "Problems found and fixed"]: an overlap resolver that always kept the *earliest* span instead of the best one; Presidio's DEA-licence checksum matching inside MRNs; a UK NHS-number recognizer firing on US phones; "MD" tagged as Maryland; spaCy splitting every address into a "person" (street) and a "place" (city), which left 64% of address characters visible; and Presidio compiling patterns case-insensitively, so `[A-Z]` matched lowercase words.

Realistic-set F1 went from 0.838 (original evaluation) to 0.893 (Day 1 fixes) to **0.999**.

### 4.2 Retrieval [PROGRESS §6]

- **Chunking:** one chunk per note section (18,003 chunks, 7.2 per note), each prefixed with a non-PII context line (note type, visit date, diagnosis). Sections keep the context small and make every citation a short paragraph a human can check.
- **Search:** dense (`BAAI/bge-small-en-v1.5`, exact cosine similarity) and an in-house BM25, combined by weighted reciprocal rank fusion. The 2:1 weighting was chosen on dev (evidence 0.968 vs 0.943 at 1:1). Dense and hybrid are statistically tied on test; hybrid is kept because BM25 matches exact strings when no filter applies.
- **Query analysis:** diagnosis and date filters (ISO, US, written, month, year, ranges, abbreviations), a residual ranking query with the constraints removed, scope-dependent k, and an ask/condition split. Without query analysis answerable evidence is 0.103; with it, 0.949.
- **Selection:** placeholder-only sections (headers, signatures) are demoted; notes contribute at most two chunks, ordered by their best chunk; for multi-patient questions each chosen note's second slot goes to its best section for the *ask* ("which medications"), because the qualifying symptom and the answering medication live in different sections (two-hop). Aggregate evidence rose from 0.553 to 0.847 at the same context size (Figure E6).
- **Access control and logging:** the raw index opens only with explicit baseline access; every query is logged with filters, scores and ranks of each returned chunk.

### 4.3 Generation [PROGRESS §7.1–7.3]

The model receives numbered sources `[C1] (Note 1) …` and must reply with JSON `{answer, claims[{text, citations}], insufficient}`. "Note n" is an opaque per-prompt number that lets the model connect a note's symptom to its own plan without seeing any identifier. Malformed output is retried once; citations to sources that weren't shown are dropped and recorded. Three prompts were compared on dev (v2 chosen: 0.941 vs 0.890 for v1 and 0.924 for v3).

The **abstain guard** runs before the model. It was introduced because the model treats `[NAME]` as whoever the question names: with the guard off it answers all 84 identity test questions, every one from another patient's note.

### 4.4 Verification [PROGRESS §7.4–7.5]

For each claim, the cited chunk is the NLI premise and the claim the hypothesis; with several citations, each chunk alone and all together are tried and the best-supporting premise is used. The model (DeBERTa-v3-large trained on MNLI/FEVER/ANLI/LingNLI/WANLI) and the UNCERTAIN margin were chosen on the dev half of a **corrupted-claim set** of 1,289 items built from the system's own answers: genuine claims, plus corruptions with known ground truth (drug swap, dose change, number change, negation, symptom swap, an invented extra drug, and the evidence swapped for another patient's note). The chosen margin is 0: the large model's errors are confident, so no margin separates them from correct labels, and UNCERTAIN does not occur in practice.

### 4.5 Audit trace and dashboard [PROGRESS §14]

Each question produces one trace JSON (~9 KB): the redacted question and the identifier types removed; query analysis; every chunk shown to the model with dense, BM25 and fused scores and ranks; the raw model output, parsed claims and citation map; each claim's NLI label and probabilities; and per-stage timings. On redacted configurations the original question is never written anywhere (tested with six PII-bearing questions). A Streamlit dashboard (local-only, telemetry off) has a live demo page, an audit view that renders a trace stage by stage with citations linked to chunk cards, a table of all stored evaluation traces, and an experiments page with the figures.

## 5. Results

All on the realistic test split unless stated. Figures in `glassbox/results/figures/`; tables in `glassbox/results/figures/tables.md`.

### 5.1 Privacy

| | GlassBox | Raw baseline |
|---|---|---|
| Redaction F1 / values fully masked | **0.999** / 0.991 | n/a |
| PII values visible in the index: fully / any part | **0.01% / 0.04%** | 100% |
| Identity questions answered (of 84) | **0** | 42 |
| …of which the person's true value, cited from their own note | **0** | 16 |
| Identity lookups possible by keyword search (BM25) | **0.000** | 1.000 |
| PII values in 9,630 log and trace records (realistic) | **0** | 7,952 (positive control) |

- **Figure E1a** gives F1 and full masking per PII type; names are the weakest (0.998 F1, 0.974 fully masked, usually a title or one name part left).
- **Figure E5**: GlassBox answers no identity question; with the guard off the model answers all 84, from other people's notes; the raw baseline answers half and leaks the true value in 16.
- **Log scan** [PROGRESS §14.3]: every log, trace and committed answer file was searched for all 17,603 ground-truth PII values, the original identity questions, and name parts. The first scan found a real leak: early prompt-development logs (written before a question-name rule existed) contained one synthetic patient's name. It was scrubbed and the rule fixed; the raw-baseline files serve as a positive control that the scan can find PII.

### 5.2 Utility

**Figure E3**: answer in retrieved context 0.949 vs 0.907; answer correct 0.919 vs 0.899; grounded accuracy **0.858** [0.815, 0.899] vs **0.833** [0.788, 0.877]. The confidence intervals overlap, so redaction has no measurable cost. GlassBox scores slightly *higher* not because redaction adds information, but because low-information demotion can only recognise header sections once their values are placeholders; in the raw index those sections hold real names and compete for slots. The report should say "no measurable cost", not "redaction helps".

By question type: clinical facts 0.976 grounded; aggregates 0.622, against a retrieval ceiling of 0.847. The 7B model drops a qualifying patient's drug or includes one from a note that doesn't meet every condition.

Data minimisation: about 955 characters of context per question, against 2,598 for whole-note retrieval (which finds every answer but shows the model 2.7× more text, including every other section of each note) [PROGRESS §6.8].

### 5.3 Privacy-utility trade-off: redaction threshold

**Figure E4.** The whole pipeline (redaction of 2,500 notes, a new index, retrieval and generation) was re-run at six detector-confidence thresholds. Every metric is identical from 0.4 to 0.7, so the chosen 0.5 sits on a stable plateau. At 0.3, context-gated recognizers fire without context and remove clinical text 4,219 times. At 0.8, the context-boosted phone pattern (0.40 + 0.35 boost) no longer fires: 15.6% of phone numbers leak and character leakage rises from 0.24% to 1.85%. Grounded accuracy doesn't move at 0.8 because no question asks about phone numbers, so the upper bound has to be set by the privacy metrics, which is itself a finding about evaluation design [PROGRESS §5.1].

### 5.4 Faithfulness

**Figure E7a:** 99.4% [98.8, 99.9] of corrupted claims are not marked SUPPORTED; every dose change, number change, negation, symptom swap and invented drug is caught; drug swaps 97.0%; wrong citations 99.4%. Clean genuine claims wrongly flagged: 1.2%. Counting all genuine claims, 8.8% are flagged, almost all because the generator restated the question's condition ("…patients who presented with dyspnea in September 2024") while citing only the medication section; the verifier is right that the citation doesn't support the whole claim. Both rates are reported; ground truth was not relabelled after seeing results.

**Figure E7b:** on real answers, VERIFIED answers (165) have grounded accuracy 0.906 and NOT_VERIFIED answers (21) 0.492, so the verdict is a useful signal to the user about which answers to trust.

**Verification cannot catch misattribution** [PROGRESS §7.5]. On the guard-off answers to identity questions, all 118 claims are SUPPORTED: the evidence does say what the claim says, it just isn't about the person asked about, and redaction removed the only thing that could show that. Rewriting the claim's subject to "the person named in the question" lowers this only to 78 of 118, and that rewrite can only fire when an identifier was detected, which is exactly when the guard has already refused. **Identity protection must happen before generation; claim verification checks evidence, not identity.**

### 5.5 Retrieval design ablation

**Figure E6:** answerable evidence 0.840 (initial design) → 0.854 (+ low-information demotion) → 0.919 (+ note-ordered grouping) → **0.949** (+ two-hop answer sections). The final CI [0.922, 0.972] does not overlap the initial one [0.792, 0.885]. Question redaction alone changes nothing for clinical questions, as intended.

### 5.6 Replication on the second dataset (E9)

The full pipeline was run unchanged on the second dataset (250 synthetic notes from a different generator, 160 questions; nothing tuned on it). Test split: GlassBox grounded accuracy **0.942** [0.896, 0.981] vs **0.916** [0.864, 0.961] for the raw baseline; identity questions answered **0 of 35** vs 25 of 35; VERIFIED answers 0.960 accurate. The comparison replicates. Absolute numbers are higher because these notes are single short paragraphs, so this confirms the *pattern*, not robustness to harder input (that is §6). [PROGRESS §15.1; `tables.md` E9]

The log scan of these traces also produced the clearest example of why redaction recall matters end to end: the one synthetic patient name the redactor misses (1 of 838 values) was retrieved for two questions, and in one of them the model copied it into a claim. The scan flagged it; it is reported, not hidden. [PROGRESS §14.3]

### 5.7 Cost

Median 3.2 s per question on an Apple-silicon laptop when the model runs: question redaction 4 ms, retrieval 6 ms, verification 37 ms, the rest generation. Privacy and verification together add under 2% to response time. Refused questions return without calling the model.

## 6. Robustness, overfitting and methodological checks [PROGRESS §8, §14.6]

### 6.1 Protocol

Every number above is measured on text produced by our own generators, and several components were developed while looking at that data. To test whether the numbers measure the system or the templates, two kinds of test set were built: **set A** for development (finding problems and fixing them) and **set B**, held out, committed to git before any fix (commits `2f0bb6b`, `a0047eb`) and evaluated once. No fix was made after seeing set B.

### 6.2 Findings

| | Template | Set A before → after fixes | **Set B (held out) before → after** |
|---|---|---|---|
| Retrieval evidence, reworded questions | 0.949 | 0.450 → 0.932 | **0.324 → 0.579** |
| Grounded accuracy, reworded questions | 0.858 | | **0.502** |
| PII values fully masked, new note formats | (0.991) | 0.815 → 0.986 | **0.672 → 0.819** |

(**Figure E8**, table E1b.) The rule-based query analysis covered the date and diagnosis formats its author thought of; held-out wording used others ("29-Sep-2024", European day-first dates, "w/"). Redaction fixes generalised for dates of birth (0.32 → 1.00 on set B) and IDs (0.03 → 0.70), but not for PO boxes or multi-line addresses (0%).

**Bias by name origin (Figure E1c):** on held-out notes, patient names of English or Swedish origin are fully masked 97% of the time; Spanish 73%, Vietnamese 70%, Turkish 57%. The spaCy NER under Presidio misses names from some cultures far more often. This belongs in the ethics discussion.

What held up: dev → test gaps are small (retrieval 0.968 → 0.949, generation 0.941 → 0.919); a regenerated dataset with a new seed gives redaction F1 0.999 again; the identity guard caught every phrasing tried (possessives, lowercase, titles, bare IDs); no drug or symptom was redacted on any out-of-distribution set.

### 6.3 Metric gaming

Plain accuracy credited a gold item found anywhere in the answer. One aggregate answer scored 1.0 by listing four drugs from four wrong notes, and pasting all retrieved text would have scored higher than the model. Grounded accuracy (cited from a gold note) and drug-list F1 replaced it: plain 0.919 → grounded 0.858 overall, 0.757 → 0.622 for aggregates.

### 6.4 Approximate search silently weakened the baseline

While checking that the end-to-end pipeline reproduced the evaluation, raw-baseline identity questions retrieved different chunks in different runs. The cause was ChromaDB's HNSW index, an approximate nearest-neighbour search: on unfiltered questions it returned on average only 35–37 of the true top-50 neighbours (as few as 0 for one question) and was not reproducible across processes. Replacing it with exact search (a NumPy matrix product, also faster: retrieval 29 ms → 6 ms) left every GlassBox number unchanged, because its answerable questions are filtered and filtered search was already exhaustive, but made the no-privacy baseline *stronger*: its hybrid identity recall rose from 0.333 to 0.548, and it now answers 42 of 84 identity questions, 16 with the person's true value from their own note. Two full re-runs from scratch were then identical. The lesson for the report: an approximate index can quietly change an experimental comparison, and an end-to-end reproduction check is what exposed it.

## 7. Discussion

- **Privacy and utility were not in tension here.** Minimal, redacted context lost no measurable accuracy, and filters derived from non-PII metadata did most of the work. The real trade-off appeared elsewhere: whole-note retrieval finds every answer but shows 2.7× more text.
- **Where protection actually comes from.** Redaction of notes blocks identity lookups at retrieval (0.000 recall), but the model would still happily attribute someone's note to whoever the question names. Only the pre-generation guard prevents that, and verification cannot substitute for it.
- **What verification is good for.** It reliably catches claims that misstate their evidence and gives the user a meaningful trust signal (0.906 vs 0.492), but only relative to the cited text.
- **Generalisation is the main weakness.** Rule-based query analysis and pattern-based redaction are auditable and fast but cover the formats their author anticipated; the held-out numbers (0.502 grounded accuracy, 0.819 masked) are the honest ones to quote for unseen input.

## 8. Related work and positioning

- **PII detection in clinical text.** Presidio (Microsoft) combines NER and regex and is production-ready but general-purpose; clinical de-identification models trained on i2b2 data reach high recall but need labelled data. GlassBox uses Presidio as a base with healthcare-specific recognizers and a clinical-term guard.
- **Privacy-preserving LLM pipelines.** Differential privacy gives formal guarantees at a utility cost and is hard to tune; federated learning targets training rather than inference over a central store; homomorphic encryption is orders of magnitude too slow for LLM inference. GlassBox's redaction is not formally private but is practical, fast and fully inspectable.
- **Explainability and verification.** RAG frameworks with citations (LangChain, LlamaIndex) let the model self-report sources without independent checking. NLI-based fact checking uses an entailment model as an independent judge. GlassBox integrates cited generation with independent NLI verification and an audit trail, and measures where that verification stops working (misattribution).

## 9. Limitations

- Synthetic, template-generated data; held-out wording and formats show substantial drops (§6).
- Redaction misses PO boxes, multi-line addresses and addresses without a ZIP on unseen formats, and masks names of some origins less reliably.
- Titles kept next to `[NAME]` ("Mrs. [NAME]") reveal gender and are a quasi-identifier.
- The redaction audit log stores original PII by design; it is itself a sensitive artifact.
- The verifier's errors are confident, so UNCERTAIN never fires; 13% of genuine multi-hop claims cite incompletely.
- No formal privacy guarantee; no role-based access control; one local 7B model.

## 10. Future work

- Query understanding that generalises: a date-parsing library, trying both day/month orders when one matches no note, or LLM-based query parsing (less auditable).
- Redaction: PO boxes and multi-line addresses; a name-origin bias mitigation (e.g. a multilingual NER model); redacting titles with names.
- Generation: a prompt rule to cite every section a claim relies on (fixes the incomplete-citation false alarms).
- Pseudonymisation (consistent fake names) instead of type tags, to preserve which mentions refer to the same person.
- Validation on real de-identified data (e.g. MIMIC) with approval; formal privacy mechanisms on top of redaction.

## 11. Conclusion

GlassBox shows that a local question-answering pipeline can enforce data minimisation and verifiable citation together without a measurable cost in answer quality on in-distribution data, and that each protection can be measured rather than assumed. The evaluation also locates the limits precisely: identity protection must be a rule before generation, because evidence-based verification cannot see who an answer is about; and rule-based components that look near-perfect on their own templates lose much of that accuracy on held-out wording and formats.

## Appendix A: Reproducing the results

```bash
python -m glassbox.src.generate_realistic_dataset --size large
python -m glassbox.src.redaction.pipeline --dataset realistic
python -m glassbox.src.retrieval.index --dataset realistic --all
python -m glassbox.src.retrieval.evaluate --dataset realistic
python -m glassbox.src.generation.evaluate --dataset realistic          # ~1 h
python -m glassbox.src.verification.corruptions && python -m glassbox.src.verification.evaluate
python -m glassbox.src.experiments.threshold_sweep                      # ~2 h
python -m glassbox.run --qa-set [--config raw|redacted_noguard]
python -m glassbox.src.experiments.log_pii_scan
python -m glassbox.src.experiments.figures
python -m glassbox.verify                                               # live check: stored results = current code
```
